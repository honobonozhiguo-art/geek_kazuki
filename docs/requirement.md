# 要件定義:半日おでかけコース提案アプリ(仮)

Flask + LLM で作る、外出先の意思決定支援アプリ。
プログラミングスクールAIコースの課題作品として、デモで伝わることを最優先とする。

---

## 1. 背景と課題

### 一次情報(ユーザーヒアリングで得られた事実)

- 「外出したいが、どこに行けばいいか迷う」
- 迷う理由は選択肢不足ではなく **決定麻痺**(多すぎて決めきれない)
- 決めきれない根本には「失敗したくない」「おもしろくなかったらどうしよう」がある
- **調べるのがだるいのが最大の障壁**
  - 地図を見て、Instagram を見て、ルートを調べて、運賃を調べて…と複数アプリを行き来する必要がある
- **すぐ終わってしまって暇になる** のが不安
- 1人だと結局出かけない。友達に誘われたら行く
- 友達と行った場合は場所が微妙でも満足している
  → **同行者がいる時の満足は「人といる時間」由来であり、場所の質とは別軸**
- 雨なら雨で行ける場所を提案してほしい
- 所要時間は 30分程度の誤差なら許容できる

### 課題の構造

調査コストの高さが失敗への恐れを増幅し、決断を先送りさせ、最終的に外出しない、というループが発生している。

```
外出したい → あちこち調べる → 準備コストが重い
    ↑                              ↓
結局家にいる ← 決めきれない ← ハズすのが怖い
```

下調べに時間をかけるほど「投資」になり、ハズした時の損失感が増すため、かえって慎重になって動けなくなる。

### 解くべき課題(スコープ確定)

**「調べるコストをほぼゼロにし、時間がちゃんと埋まる確信を与えることで、1人でも家を出られるようにする」**

スコープ外:
- 同行者との合意形成、友達の誘い出し
- 新規性の高い場所の発掘(MVPでは同じ場所の再訪を許容する)

---

## 2. コンセプト

### 提案の単位を「場所」ではなく「半日の過ごし方」にする

1スポットの提案では「すぐ終わって暇」が解決しない。
2〜3スポットを繋いだ **ミニコース** を提案単位とすることで、以下が同時に解決する。

| 課題 | コース化による解決 |
|---|---|
| すぐ終わって暇 | 3〜4時間が埋まることが事前にわかる |
| 調べるのがだるい | 「点を繋いで半日を組み立てる」作業自体を代行する |
| 失敗が怖い | 時間・費用・移動が事前に提示され、想定外が減る |

既存サービス(地図アプリ、SNS、まとめ記事)はいずれも「点」しか提供せず、繋ぐ作業がユーザーに残っている。ここが本アプリの立ち位置。

### 差別化の核

- 目的が決まっていない人が使える(既存の地図アプリは目的が決まっている人専用)
- 選択肢を並べない。決定麻痺が課題なので、リストを出した時点で元の悩みに戻る
- 1画面で完結する(場所・順番・時間・移動・費用)

---

## 3. AI の役割(重要)

### 設計方針:実在するスポットの在庫を用意し、その組み立てだけを LLM に任せる

LLM に場所そのものを「思い出させる」と、存在しない店・閉店した店を出力する。
「行ったら閉まっていた」が1度でも起きるとアプリの唯一の価値(調べなくていい安心)が失われるため、これは絶対に避ける。

| LLM に任せる | データとして持つ(生成させない) |
|---|---|
| スポットの選択と並び順 | 店舗が実在するか |
| 時間配分の計算 | 営業時間・定休日 |
| コース名と説明文の生成 | 所在地・最寄駅 |
| 自由文入力の解釈 | 移動時間・運賃の目安 |
| 「なぜ今日これなのか」の理由づけ | 屋内/屋外の別 |

### 処理の流れ

```
ユーザー入力(自由文 + 日付/時間)
        ↓
spots.json から候補を渡す
        ↓
LLM がコースを組み立てる
  ・条件に合うスポットを2〜3件選ぶ
  ・順番と時間配分を決める
  ・コース名と説明文を書く
        ↓
JSON で受け取り、画面に表示
```

この構成は、外部データを検索して生成に与える RAG の考え方に近い。
「AI にすべてを任せず、事実はデータ、判断と表現は AI」という役割分担そのものが本作品の設計上の主張であり、プレゼンで説明すべきポイント。

## 4. 機能要件

### 4.1 入力

- **自由文入力(必須)**
  - 例:「今日ちょっと疲れてる。あんまり歩きたくないけど夕方まで暇」
  - 曖昧な言葉を条件に翻訳できるのが LLM の価値であり、デモの見せ場
- **日付/時間の簡易選択**
  - 今日 / 明日
  - 空いている時間(2時間 / 半日 など)
- **天気の切り替え(晴れ / 雨)**
  - MVP では天気 API を叩かず手動切り替えとする
  - デモ中に目の前で結果が変化するため、むしろ演出として強い

入力から結果表示まで **3タップ以内** で完了すること。
このアプリの主張が「調べるのがだるい問題の解決」である以上、入力が面倒だと主張と矛盾する。好み設定画面などは作らない。

### 4.2 出力(コースカード)

1件のみ表示する。複数の選択肢を並べない。

必須表示項目:
- コース名(AI 生成)
- 出発時刻 → 帰宅時刻、合計滞在時間
- 往復運賃の目安 / 片道の所要時間 / 想定出費
- 各スポット(2〜3件)
  - 時刻
  - スポット名
  - 一言説明(移動手段、所要目安、AI が書いた理由)
- 適用された条件のバッジ(例:「今日は雨 · 全部屋内」「1人向け」)

操作:
- 「別の案」ボタン(再生成)
  - 押せる回数は絞る。無限に出せると決定麻痺に戻る

### 4.3 データ(spots.json)

スポット30件程度を手動で用意する。エリアは1つに限定する。

各スポットの想定項目:

| 項目 | 例 | 用途 |
|---|---|---|
| name | 〇〇書店 池袋店 | 表示 |
| area / nearest_station | 池袋 | 移動時間の算出 |
| category | 書店 / 喫茶 / 雑貨 | 組み合わせの多様性確保 |
| indoor | true / false | 雨の日の絞り込み |
| avg_stay_min | 55 | 時間配分の基礎 |
| open_hours | 10:00-21:00 | 営業時間の判定 |
| closed_days | 火 | 定休日の判定 |
| solo_friendly | true | 1人で入りやすいか |
| note | 長居しやすい / 駅直結 | AI が説明文を書く材料 |

`avg_stay_min` は正確な実測値である必要はない(誤差30分は許容される)。カテゴリごとの相場を手で入れて構わない。

## 5. 技術構成

### スタック

- Python / Flask
- LLM API(Anthropic Claude を想定)
- フロント:Jinja2 テンプレート + CSS フレームワーク1つ
- データ:`spots.json`(データベースは使わない)

### ファイル構成(想定)

```
app.py             ルーティング、LLM 呼び出し
spots.json         スポット30件
prompt.py          プロンプト組み立て(app.py 内でも可)
templates/
  index.html       入力フォーム + 結果表示
static/
  style.css
.env               APIキー
.gitignore         .env を必ず含める
requirements.txt
```

### Flask を使う理由

API キーをブラウザに露出させず、サーバー側に隠すため。
フロントだけで作ると誰でもキーを閲覧できてしまう。これが本課題でバックエンドを設ける理由であり、説明できるようにしておく。

### エンドポイント

| メソッド | パス | 役割 |
|---|---|---|
| GET | `/` | 入力フォーム表示 |
| POST | `/suggest` | 条件を受け取りコースを生成して表示 |

## 6. 実装上の注意(先に潰しておくべき点)

### 6.1 LLM が素直に JSON を返さない

ほぼ確実に発生する。対策:

- プロンプトで「JSON のみを出力。前置き・説明・コードフェンスを一切つけない」と明示する
- 出力形式のサンプル JSON をプロンプト内に示す
- パース失敗を前提に `try/except` を書き、失敗時は固定のフォールバックコースを返す
  - **デモ中に一発でコケるのが最悪のシナリオ。フォールバックは必須**

### 6.2 生成に時間がかかる

5〜15秒かかることがある。無反応だと「壊れた」と見える。

- ローディング表示を必ず入れる
- デモで使う条件は事前に生成して保存しておいてよい(キャッシュ)
- ローディングをわざと長く見せる演出はしない。速いことは武器

### 6.3 API キーの管理

`.env` + `.gitignore` を最初に作る。キーをリポジトリに含めない。

### 6.4 表記について

- ○「AI が組み立てたコース」「AI があなたの条件に合わせて選びました」
- ×「たった今あなたのために生成しました」(キャッシュを返す場合は事実と異なる)

## 7. スコープ外(MVP では作らない)

- データベース
- ユーザー登録 / ログイン / 履歴保存
- 経路検索・運賃 API 連携(spots.json に手書きの目安を持つ)
- 天気 API 連携(手動切り替えで代替)
- 地図表示
- 複数エリア対応
- お気に入り、共有機能
- デプロイ(ローカルでデモ可能なら任意)

## 8. 完成の定義

以下のデモが最後まで通ること。

1. 「休みの日、外出たいけど結局家にいたことない?」と課題提起
2. 「地図見て、インスタ見て、ルート調べて…がだるい」と具体化
3. 自由文を入力 → コースが1件表示される
4. 天気を「雨」に切り替える → 屋内だけのコースに変わる
5. 「1人でも3時間半、ちゃんと埋まります」で締める

3 と 4 で驚きが起きれば成功。それ以外の機能は評価に寄与しない。

---

## 9. 進め方(推奨順)

1. `spots.json` の項目を確定し、まず3件だけ書く
2. Flask を使わず、Python スクリプト単体で LLM にコースを組ませる
   → **ここが最大の関門。JSON が安定して返るまでここに集中する**
3. 動いたら Flask に乗せる(GET / と POST /suggest)
4. spots.json を30件に増やす
5. 見た目を整える
6. フォールバックとローディングを入れてデモ耐性を上げる

ステップ2をクリアした時点で、作品としてはほぼ完成が見えている。
